# Decisions

Each row: what this project uses → why. The template started as a port of a Nuxt baseline; on
2026-10-05 the data layer was refactored into a server-only DAL with Server Actions, Zod DTOs,
Prisma 7 and Better Auth, and on 2026-10-09 it was cut back to its core (see **Removed** below).

## shadcn reset

The UI uses stock Base UI primitives (`base-vega`, the classic shadcn look) installed through the
official shadcn CLI. They replaced the Radix/New York set on 2026-10-10: shadcn defaults new projects
to Base UI, `new-york` has no Base UI variant, so `components.json` moved to `base-vega` and the 17
untouched primitives were deleted and re-added with `shadcn add`. Call sites moved from `asChild` to
`render`; links styled as buttons use `ButtonLink` (`buttonVariants` on `next/link`), because Base
UI's Button forces `role="button"`.
`components.json` points to `styles/global.css`; the token values and fonts come from the
[zippystarter theme](https://zippystarter.com/r/nw0r02zop7mgg0ba1u1fjou6), installed with
`bunx shadcn@latest add` on 2026-10-10 to replace the stock neutral palette. After the install, the
CLI's self-referencing `--font-*` theme entries were dropped, the invalid `tight` tracking became
`-0.025em`, and `--font-sans` points at Geist, so Inter is gone. The `--radius-*` scale moved
into its own `@theme static inline` block: Tailwind drops theme variables no utility uses, which
left `var(--radius-xl)` undefined for CSS Modules (corners rendered square). Only Prettier formatting
is applied to generated components, so CLI updates do not erase app logic. Labels/errors and loading
behavior live in separate application wrappers. `lib/utils.ts` stays CLI-owned. Theme support follows
the [official Next.js guide](https://ui.shadcn.com/docs/dark-mode/next): `next-themes`, a class-based
provider with system default and transition suppression, and a light/dark/system menu. The site is
pinned to dark for now (`PINNED_THEME` in `lib/constants-theme.ts`, a `forcedTheme`), with the menu
hidden rather than deleted so the choice can come back with one line.

| Roles and admin        | Better Auth's **`admin` plugin** with three roles, `roles: { viewer: userAc, editor: userAc, admin: adminAc }`, `defaultRole: 'viewer'`, `adminRoles: ['admin']`; a `users_role_valid` CHECK constraint on the same three. `requireAdmin()` is `role === 'admin'`. `lib/data/admin.ts` wraps `auth.api.setRole` / `banUser` / `unbanUser` / `impersonateUser` behind `requireAdmin()` plus "not your own role"; `listUsers` is our own query                                                                                                                                                                                         | The plugin owns the semantics that are easy to get wrong (a ban revokes sessions and blocks sign-in; impersonation keeps the admin session aside). Only admins hold the plugin's permissions; what an editor may do with movies is this app's policy, not the plugin's. Listing `roles` types `setRole` to our roles and makes the plugin refuse others; `role` is text in the plugin, so the DAL also narrows it with `roleSchema` and treats anything unknown as `viewer`.                                                                                                                                                                                                                                                                                                                  |
| Ids                    | UUIDv7 everywhere (`@id @default(uuid(7)) @db.Uuid`), generated by Prisma Client; Better Auth's `advanced.database.generateId: 'uuid'` leaves its ids to Prisma; id schemas are `z.uuid()`. Integer ids were considered for the catalog and rejected: they are enumerable (row counts and creation order leak through the URL), they would put two id types and two id schemas in one DAL, and the slug already gives readable URLs. Cost: a UUIDv7 reveals its creation time, and a malformed id must be validated before it reaches PostgreSQL, which throws on it.                                                                                                                                                                                                 |

| Writes                 | Server Actions with no wrapper library; they hand their arguments to the DAL                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Fewer moving parts. | Input validation       | In the DAL: each function runs `parseInput(schema, input)` after the session check. Actions pass arguments through; only `actions/auth.ts` parses itself, because it calls Better Auth directly                                                                                                                                                                                                                                                                                                                                                                                                                                      | The DAL is the one layer every caller shares, so validation there cannot be skipped, the same reason auth lives there. Accepted: a Route Handler parses twice (once to decode the query string, once in the DAL).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Data access            | `lib/data` DAL, `server-only`, the only Prisma importer (lint-enforced)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | One place for queries, mapping, and auth (Next's data-security guide).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Authorization policies | `lib/data/policy.ts` (`Rule`, `authorize`, `permissionsFor`) and one pure policy object per resource in `lib/data/policies/<resource>.ts`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Pure functions of `(viewer, record)` are testable per viewer without a database, and the DAL keeps the order 401 → 422 → 404 → 403. | Errors                 | Typed DAL errors → `ActionResult` / HTTP 401-403-404-422-429 / redirect or `notFound()`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Each caller translates once; forms map `fieldErrors`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Pagination             | `Page<T> = { items, page, perPage, totalItems, totalPages }` (`OFFSET` / `LIMIT`), `page` capped at 1000; every sort ends with `id` as the tiebreaker and has a matching `(column, id)` index                                                                                                                                                                                                                                                                                                                                                                                                                                        | Admin tables use numbered pages. | Catalog search         | `ILIKE '%term%'` on `movies.title` and `people.name` through `pg_trgm` GIN indexes; a term is at least 3 characters (`searchTermSchema` in `lib/dto/common.ts`, used by `listMoviesQuery`, `listPeopleQuery` and `searchCatalogQuery`; the URL twins fall back to no search). Prisma cannot order by an expression, so the ranking is the one raw query the catalog has (tagged template, rows parsed with Zod); it selects ids only and the rows come back through the lists' selects, so the DTO mapping is written once. | Release date           | `movies.release_date` is `DATE NOT NULL`; the catalog holds released films only (decided 2026-10-10)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Every row sorts by a real date, so the default "newest" order needs no `NULLS LAST` and no placeholder date. | Search and filters     | IMDb's two surfaces: a NavBar search box with suggestions (`SiteSearch`, `useDebouncedSearch`) whose Enter is a plain `GET /search?q=` through `next/form`, and a `/search` page that groups the best movies and people with scope links to `/movies?q=` and `/people?q=`; the movie list is the advanced search (`MovieFilters`): title, `genres=a,b` (every genre named), `yearFrom`/`yearTo`, `runtimeMin`/`runtimeMax`, `person`, `sort`, all in the URL (`moviesUrlQuery`, `toListMoviesQuery`), with a chip per filter in force; the title search and sort apply at once, the panel applies on its button (decided 2026-10-10) | A search box that suggests as you type is what visitors expect from a catalog, and a results page they can share needs a real URL, so Enter submits a form rather than calling a router. ## API documentation

`GET /api/openapi` generates OpenAPI 3.1 with `zod-openapi` from the shared Zod DTOs.
`GET /api/docs` serves standalone Scalar HTML through `@scalar/nextjs-api-reference`, with the
browser renderer pinned to `@scalar/api-reference@1.73.1`. Both documentation routes are public in
all environments. The spec URL and API server URL are relative so requests stay on the current
origin; Scalar's external request proxy and telemetry are disabled.

The spec covers the existing public `GET /api/v1/people` and `GET /api/health` handlers. The generator
imports DTOs only, so reading documentation does not initialize auth, PostgreSQL, or Redis. Numeric
query schemas use their parsed output representation for integer bounds and defaults, while retaining
the original input optionality. Response dates are documented as ISO date-time strings to match JSON
serialization. Search refinements that JSON Schema cannot express are described alongside the query.

Account operations use Server Actions. Selected Better Auth account HTTP routes are intentionally
disabled in `lib/data/auth.ts` to enforce application rules. All authentication operations are excluded
from the spec; the introduction links to the
[upstream Better Auth documentation](https://www.better-auth.com/docs). API keys remain deferred.

## Deferred

Left out on purpose; add them when a project needs them.

- **Organizations (teams, membership, per-tenant data):** every query would gain a tenant key and every
  policy a membership check, which changes the shape of the whole DAL. That is a design decision for
  the project that needs it, not something to leave half-wired in a template.
- **API keys:** no API-key authentication is configured; the existing documented reads are public.
- **Page transitions between the movie card and the detail page:** tried with React's
  `<ViewTransition>` (a shared poster morph plus a content crossfade) and taken out (2026-10-10)
  because it looked wrong. Notes for the next attempt: it only feels instant when the destination is
  already in hand at the click (`prefetch` the full dynamic route; prefetching is off in `next dev`, so
  judge on a production build); React waits for images to decode before the snapshot but skips
  `loading="lazy"` ones; crossfading two snapshots of the same poster shows a mid-flight re-render;
  every layer must run on one clock; and stable React in Vitest has no `ViewTransition`.
- **End-to-end browser tests:** the suite stops at Vitest (DAL, actions, handlers, components).
- **A last-admin guard on account deletion:** only an admin changing their own role is blocked; the
  last admin can still delete their own account.
